## 🐛 问题修复与复盘

- **采购页面状态不一致**
  - 问题现象：当没有未来计划时，采购页面仍显示历史的"已加入黑名单"和"本次已采购"卡片，状态混乱。
  - 根本原因：后端自动清空任务时，未同步清空 `completed_items` 和 `removed_ingredient_ids`，而是保留了旧数据。
  - 最终解决方案：修改后端 `GET /api/shopping/task` 接口，在自动清空任务时，将所有四个列表字段都设为空数组 `[]`，确保前端状态统一。

- **RPC 调用错误处理不统一**
  - 问题现象：不同路由的 RPC 调用错误处理方式不一致，日志格式不统一。
  - 根本原因：缺少统一的错误处理规范。
  - 最终解决方案：统一所有 RPC 调用的错误处理，日志格式统一为 `logger.error(f"[函数名] 失败: 参数=xxx, 错误={str(e)}", exc_info=True)`，失败时返回简洁的 HTTP 500 错误提示。

- **数据库函数查询逻辑错误**
  - 问题现象：SQL 函数查询 `status` 字段时使用字符串 `'active'`，但数据库字段类型为布尔值。
  - 根本原因：001 和 002 SQL 迁移文件中的查询条件类型不匹配。
  - 最终解决方案：将 `status = 'active'` 改为 `status = TRUE`，与字段类型保持一致。

- **采购页面数据加载逻辑问题**
  - 问题现象：采购页面无法根据未来计划动态过滤待购项。
  - 根本原因：原接口未实现根据未来计划过滤 pending_items 的逻辑。
  - 最终解决方案：重构 `GET /api/shopping/task` 接口，实现：
    1. 一次性查询活跃任务和未来计划
    2. 如果无未来计划 → 清空并完成任务
    3. 如果有未来计划 → 过滤 pending_items，只保留与未来计划相关的项
