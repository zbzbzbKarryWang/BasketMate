【AI 交互规则】
1. 对于用户给出的明确、具体的代码修改指令，请直接执行修改，无需逐行向用户请求确认。
2. 仅在遇到以下情况时，才需要暂停并询问用户：
   - 指令描述模糊，存在多种可能的技术实现方案。
   - 修改可能会影响项目的核心架构或安全。
   - 缺少完成修改所必需的信息（如数据库密钥、API 端点等）。

【通用开发约束】

1. **命名与数据源一致性**
   - 所有代码中的字段名、JSON Key、变量名，**以数据库实际定义为准**（下划线 snake_case）。禁止混用驼峰 camelCase，除非数据库已存在且无法修改。
   - 接口请求/响应字段、Pydantic 模型字段必须与数据库列名完全一致。若发现不一致，必须先询问我确定以谁为准。

2. **路径与配置一致性**
   - 任何文件读写路径（日志、静态资源、挂载目录）必须与 `docker-compose.yml` 的 volumes 映射和 `Dockerfile` 的 WORKDIR 保持一致。
   - 若涉及路径不确定，先检查现有 Docker 配置或询问我。

3. **错误预防**
   - 禁止使用已废弃的 API（如 Supabase 的 `response.error`，FastAPI 的 `content_type` 参数），应使用当前版本推荐写法。
   - 修改 Pydantic 模型后，必须同步检查所有引用该模型的接口和前端代码。
   - 前端组件内使用的任何变量（如 `removedItems`）必须先定义再使用，确保从正确的 state/props 派生。

4. **性能基线**
   - **严禁在循环内进行数据库查询**（N+1 问题）。必须使用批量查询（如 `.in_()`）后，在内存中组装数据。

5. **日志与可观测性**
   - 后端每个新增或修改的路由，必须添加结构化的 `logger.info()` 日志，包含操作名称和关键参数/结果。
   - 日志路径必须与 Docker 配置一致，写入前确保目录存在。
   - 后端日志中间件必须根据 HTTP 状态码自动选择日志级别（2xx→INFO，4xx→WARNING，5xx→ERROR）。
   - 所有返回 4xx 或 5xx 的接口，必须在返回前记录详细的错误日志，包含请求体和具体错误信息。

6. **状态与数据流**
   - 数据修改（增删改）必须先通过 API 持久化，然后等待返回结果再刷新前端，不得仅修改前端本地状态就视为完成。
   - 全局状态（如采购清单）的字段用途必须明确区分，不得混用。

7. **冲突处理**
   - 当遇到需求描述与现有代码冲突、或技术选型不明确时，**必须先停下来向我确认**，不得擅自选择。
   - 修改前先列出影响范围（哪些文件、哪些接口），等我确认后再执行。

8. **验证与清理**
   - 代码修改后，必须主动提示我如何验证（如重启哪个容器、调用哪个接口、检查哪个页面）。
   - 若替换或删除了旧字段/旧逻辑，必须确认无残留引用。
